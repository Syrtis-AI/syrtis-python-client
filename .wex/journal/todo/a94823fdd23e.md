# Moteurs PHP, JS et bundle Symfony

Porter le moteur Python (`packages/PYTHON/packages/python-engine`, ~8 000 lignes)
vers :

- `packages/PHP/packages/syrtis/php-engine`
- `packages/JAVASCRIPT/packages/syrtis-javascript-engine`
- `packages/PHP/packages/syrtis/symfony-engine`, le bundle Symfony au-dessus de php-engine

Packages à créer (dossiers par l'utilisateur) : `php-wallet`, `php-storage`,
`php-config`, `php-llm`, `js-wallet`, `js-remote`, `js-storage`, `js-config`,
`js-llm` et, en Python, `wexample-llm`.

Le moteur Python sert de référence : même contrat (l'export JSON de l'API), même
comportement, mêmes fixtures et mêmes tests.

## Décisions à prendre

- [ ] **Nœud `code`** (piste en discussion, pas figée). Chaque moteur exécute son propre langage : `code` reste du
  Python, et de nouveaux types de nœuds s'ajoutent, `code_php` et `code_js`
  (noms à confirmer), à déclarer dans l'API et le manager. Un moteur refuse au
  chargement les types qu'il ne sait pas exécuter, comme aujourd'hui. Au
  concepteur du scénario de choisir le nœud du moteur qui l'exécutera. Mêmes
  globales que le nœud Python (`input`, `output`, `helper`) pour garder le même
  modèle. Pas de bac à sable : comme `shell`, l'application qui fournit le
  nœud sait ce qu'elle exécute. Drazen reste un scénario Python tant que ses
  nœuds `code` ne sont pas réécrits.
- [x] **Couche LLM : sans LangChain, dans les trois langages.** Le moteur n'utilise
  que les adaptateurs de fournisseurs de LangChain, la couche la plus mince :
  Syrtis est lui-même la couche d'orchestration (graphe, mémoire, RAG, outils).
  Une couche à nous garantit l'iso entre les trois moteurs : le même
  `PromptsBag` produit exactement le même JSON envoyé au fournisseur. Elle envoie
  au modèle ce que Syrtis a construit, et rien d'autre.
  - Packages génériques : `wexample-llm`, `php-llm`, `js-llm`.
    `wexample/symfony-ai` pourra dépendre de `php-llm`.
  - Périmètre : OpenAI, Anthropic, Ollama ; chat, appels d'outils, sortie
    structurée (JSON Schema), embeddings ; relances, timeouts, tokens consommés.
  - Tests « golden » partagés entre langages : requête HTTP attendue pour une
    entrée donnée, sans réseau.
  - Les découpeurs de texte (`langchain_text_splitters`) sont portés dans le
    chunker de chaque moteur.
  - Iso avec le core de prod, qui garde LangChain (version d'il y a deux ans) :
    reproduire délibérément ses choix (ex. sortie structurée par appel de
    fonction chez OpenAI), vérifiés en comparant les requêtes envoyées
    avant/après sur `agent-01` et Drazen. Migration du core : décision à part.
- [ ] **Templates Jinja.** En JS, Nunjucks, quasi compatible Jinja. En PHP, Twig,
  très proche : même syntaxe, et `none` existe. À prévoir :
  - les resolvers réimplémentés avec les mêmes noms de méthodes (`.raw`,
    `find_message_by_name()`, `.data().get_dict()`…) ;
  - les filtres propres (`to_toon`…) ;
  - la relecture des valeurs rendues en littéraux Python (`True`, `None`,
    apostrophes), ce que Python fait avec `ast.literal_eval`.
- [x] **Nouveaux packages génériques** : `php-wallet`, `php-storage`,
  `php-config`, `js-wallet`, `js-remote`, `js-storage`, `js-config` (voir étape 1).
- [x] **Pas de `php-orm` ni `js-orm`.** Les moteurs PHP/JS n'ont pas de base : il
  leur faut l'import/export du format de l'API, pas un mapping ORM. Il ira dans
  `php-api-entity` / `js-api-entity`.

## Étapes

### 1. Packages génériques, en miroir des paquets Python

| Python | PHP | JS |
|---|---|---|
| `wexample-wallet` | `php-wallet` (à créer) | `js-wallet` (à créer) |
| `wexample-remote` | `php-remote` ✅ | `js-remote` (à créer) |
| `wexample-storage` | `php-storage` (à créer) | `js-storage` (à créer) |
| `wexample-config` | `php-config` (à créer, par un agent) | `js-config` (à créer, par un agent) |
| `wexample-orm` (import/export) | dans `php-api-entity` | dans `js-api-entity` |
| `wexample-llm` (à créer) | `php-llm` (à créer) | `js-llm` (à créer) |

Les storages couvrent le filesystem, pgvector et Neo4j, choisis par capacité,
et se construisent depuis une config dont les secrets viennent du wallet.

### 1 bis. `wexample-llm`, et le moteur Python sans LangChain

- [ ] `wexample-llm` : fournisseurs OpenAI, Anthropic et Ollama ; chat, outils,
  sortie structurée, embeddings ; tests golden des requêtes.
- [ ] Le moteur Python passe dessus (connecteurs, `ModelResponse`, faux modèles
  des tests) et retire `langchain-*` de ses dépendances.
- [ ] Chunker : découpeurs portés, sans `langchain_text_splitters`.
- [ ] Vérifier l'iso avec la prod : requêtes envoyées avant/après sur `agent-01`
  et Drazen, puis rapport Drazen en réel.
- [ ] `php-llm` et `js-llm` sur les mêmes tests golden (peuvent attendre l'étape 3).

### 2. Entités et import/export dans les clients

`php-client` et `syrtis-javascript-client` n'ont que 5 à 7 entités écrites à la
main (Message, Session…), et aucune du graphe de scénario (card, job, slot…).

- [ ] Écrire les entités publiques qui manquent (card, job, slot, slot_config,
  slot_message, stamps, relations, template, environment, timezone, document,
  chunk…) : à la main si c'est plus simple que de les générer. Elles sont déjà
  en `visibility: public` dans le registre. Toute nouvelle entité publique y est
  notée ainsi (cf. `local/registry/data/entity/user.yml`). Sans générateur, le
  test de dérive devient un test de cohérence : les champs de chaque entité
  doivent correspondre au schéma `data/entity/*.json` du client.
- [ ] Porter l'import/export du format de l'API (`EntityImporter`,
  `EntityExporter`, `NormalizedEntityHydrator`). Voir ce que `php-api-entity` et
  `js-api-entity` apportent déjà.
- [ ] Porter les helpers des entités (`Message::hasStampsName`,
  `Scenario::getEntrypointCards`, `SlotMessage::matches`…).
- [ ] Tests : aller-retour sur toutes les fixtures de l'API, et cohérence des
  entités avec le schéma, comme `python-client/tests/`.

### 3. php-engine, puis syrtis-javascript-engine

Porter, dans l'ordre du Python :

- [ ] Kernel, `Engine`, `EngineSession`, `EngineResponse`, et la session distante
  (mode SaaS) ;
- [ ] Exécution : `JobExecutor` (graphe via `php-graph` / `syrtis-javascript-graph`),
  `RequestExecutor`, messages bag, ports et branches ;
- [ ] Expressions : resolvers et render pass ;
- [ ] Nœuds :
  - groupe 1 (LLM, message, condition, navigate, sub_job, iterator…) ;
  - groupe 2 (http, n8n, shell, ssh, sql) ;
  - groupe 3 (documents, vecteurs, graphe) ;
- [ ] Validation au chargement (types de nœuds, `get_requirements`), `check()`,
  configuration explicite ;
- [ ] Tests : chargement et smoke test de toutes les fixtures, sur faux modèles,
  storages en mémoire et nœuds simulés, comme `python-engine/tests/`.

### 4. symfony-engine

- [ ] Configuration du bundle en YAML : storages, modèles, limites,
  `shell_working_directory`.
- [ ] Wallet alimenté par les secrets Symfony.
- [ ] Remotes (fournisseurs, storages) enregistrés dans `symfony-remote`, donc
  visibles par `remote:status`.
- [ ] Services : `Engine` injectable, sessions distantes via le client API.
